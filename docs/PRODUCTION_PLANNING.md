# 생산관리 포트폴리오 강화 — 입력·설계·검증

작성일: 2026-10-16 · [프로젝트 소개](../README.md)

## 바꾼 이유

기존 원료 소진일·발주량에서 한 단계 더 나아가, 원료 제약이 제품별 계획에 미치는 영향과 대응 선택의 결과를 설명하기 위해 개편했다. 실제 생산관리 경력이나 현장 개선 실적을 주장하는 프로젝트가 아니라 가상 사례를 이용한 의사결정 보조 도구다.

| 변경 | 의도 |
|---|---|
| 날짜·배합표·보관 구분 검증 | 불완전한 입력에서 그럴듯한 발주 숫자를 만들지 않기 |
| 냉장·냉동, 사용상태·기한·준비일 | 보유량과 생산에 쓸 수 있는 양을 구분하기 |
| 제품별 원료 배분 | 원료 부족을 계획 물량·주문 영향으로 연결하기 |
| 대응안 비교 | 서로 다른 대응을 모두 실행하라는 안내 대신 전후 차이를 검토하기 |
| 총 계획량·납기 위험 동시 표시 | 감산·지연을 숨겨 부족 해소로 보이게 하지 않기 |
| 근거 연결·누적 조치 기록 | 왜 계획을 바꿨는지 다음 검토자가 이해할 수 있게 하기 |
| 시장 데이터 독립 실행 | 참고 데이터 누락이 공장 핵심 계산을 막지 않기 |
| 기본값 저장과 알림 공유 | 화면과 자동 경보의 판단 기준을 일치시키기 |

## 현재 입력 양식

원본 CSV는 `data/company/`에 저장되고 Git에서 제외된다. 다운로드 양식은 가짜 예시이며 UTF-8 BOM을 포함한다. UTF-8·엑셀 CP949 CSV를 읽는다. 수량 단위는 kg이다.

| 파일 | 필수 열 | 선택 열 |
|---|---|---|
| 재고.csv | 기준일, 육종, 부위, 원산지, 보관, 재고량_kg | 안전재고일수, 리드타임일수, 발주주기일, 로트, 사용상태, 사용가능일, 사용기한, 단가_원kg, 해동일수, 해동감량률 |
| 입고예정.csv (파일 생략 가능) | 입고예정일, 육종, 부위, 원산지, 입고량_kg | 보관, 공급처, 발주일, 로트, 사용상태, 사용가능일, 사용기한, 단가_원kg, 해동일수, 해동감량률 |
| 생산계획.csv | 날짜, 제품, 계획물량_kg | 주문번호, 납기, 우선순위, 판매가_원kg |
| 배합표.csv | 제품, 육종, 부위, 원산지, 투입량_kg | 보관 |

- 배합표 투입량은 **완제품 1kg당 필요한 원료 kg**이다. 수율을 반영한 입력이며 앱이 수율을 추정하지 않는다.
- 육종은 돼지/소, 원산지는 국산/수입, 보관은 냉장/냉동이다. 부위 목록은 화면과 `lib/company.py`를 참고한다.
- 원료는 **육종·부위·원산지·보관** 네 가지로 구분한다. 냉동 원료를 냉장 원료 대신 자동 배정하지 않는다.
- 예전 입고·배합표에 보관 열이 없으면 다른 입력에서 후보가 **하나일 때만** 연결한다. 둘 이상이거나 알 수 없으면 오류로 중단한다.
- 재고는 **동일한 날짜의 마감 값**이어야 한다. 여러 기준일을 섞으면 중단한다. 같은 원료의 여러 로트는 각각의 사용 조건을 유지한다.
- 사용상태: 사용가능 / 검사대기 / 사용보류. **검사대기·사용보류는 수량이 있어도 사용하지 않는다.** QC·QA가 확인한 상태를 입력한다.
- 사용가능일: 입고·해동 등 준비를 마쳐 투입할 수 있는 날. 계산 시 입고일과 이 날짜 중 더 늦은 날을 적용한다. **냉동 로트에 사용가능일이 없으면** 들어온 날(재고는 기준일 다음 날)부터 해동을 시작해 해동일수 뒤에 쓴다고 계산한다(해동 규칙은 [COMPANY_DATA.md](COMPANY_DATA.md#해동-계획-냉동-원료)).
- 사용기한: 입력한 날짜까지 사용 가능하다고 가정한다. 날짜 이후 잔량은 제외한다. 가능한 로트 중 기한이 빠른 것을 먼저 사용한다.
- 예전 파일에 사용상태·사용기한이 없으면 **사용가능·기한 제한 없음으로 가정한다는 안내**를 표시한다. 실제 안전성 보증이 아니다.
- 납기 미입력은 미입력으로 표시한다. 우선순위 기본값은 100이며 작은 숫자가 먼저다.
- 누락 배합표, 음수·무한대·잘못된 숫자·잘못된 날짜는 계산을 막는다. 배합표 없는 제품을 빼고 발주 권고를 만들지 않는다.

## 날짜와 설정

- 현재 판단일은 한국 시간이다. 재고 기준일이 미래이거나 **현재보다 2일 이상 오래되면** 현재 발주 권고와 대응안 비교를 중단한다. 원료 화면의 과거 기준 참고 계산만 남긴다. 이 기준은 프로젝트의 보수적인 가정이다.
- 전일 마감 또는 당일 마감 재고에서 다음 날부터 계산한다. 과거 실제 생산·입고를 앱이 자동 추정해 재고를 갱신하지 않는다.
- 화면에서 기본값을 수정한 뒤 **저장**해야 계산에 적용된다. `settings.json`을 화면과 자동 알림이 함께 읽는다. CSV의 개별 값이 우선이다.
- 기본 안전재고일수: 국산 냉장 5 / 냉동 10, 수입 냉장 10 / 냉동 14. 입고 소요일: 국산 2 / 수입 30. 발주주기: 국산 3 / 수입 14. 모두 설명용 초기값이다.

## 두 계산의 차이

### 원료 소요·재고: 발주 참고 계산

생산계획 × 배합표로 원료별 소요량을 계산한다. 사용 가능 로트·입고에서 차감하며 미충족 소요는 음수 잔고로 표현한다. 60일 그래프는 계획을 모두 이행할 경우의 순수급 참고선이지 실재고 예측이 아니다.

계획이 끝난 뒤는 계획 기간의 하루 평균으로 연장한다는 가정을 유지한다. 안전재고 = 첫 7일 평균 소요 × 안전재고일수. 발주량은 입고 시점 목표 재고와 예상 순수급의 차이를 100kg 단위로 올린 참고값이다. 입고 시점이 계산 범위를 벗어나면 권고하지 않는다.

긴급 확보·입고 앞당김·정규 발주를 동시에 더하라는 뜻이 아니다. **대응 선택 후 재계산**해야 한다. 최소 발주량, 공급처 한도, 가격, 창고 용량 등은 반영하지 않는다. 시장 가격은 계산에 영향을 주지 않는 참고 정보다.

### 생산 차질·대응안: 원료 기준 생산 가능량

명시된 생산계획만 사용하며 평균으로 연장하지 않는다. 날짜별로 우선순위 → 납기 → 원본 행 순서로 배정한다. 제품에 필요한 원료 중 가장 부족한 원료가 생산 가능량을 제한한다. 같은 원료를 여러 제품에 중복 배정하지 않는다.

- kg 단위 부분 생산을 허용한다. 최소 배치 크기·설비·인력·세척 전환·포장재 제약은 제외한다.
- 부족분은 다음 날로 자동 이월하지 않는다. 생산일 변경은 사용자가 대응안에서 명시한다.
- 납기 위험은 원료 부족이 있거나 생산계획일이 납기보다 늦은 경우다. 실제 납품 완료나 지연 일수를 보장하지 않는다.
- 대응안은 기존 계획·입고·배합표의 복사본이다. 입고 앞당기기, 추가 확보, 생산일·수량·우선순위 변경, 대체 배합을 조합할 수 있다. 원본 CSV에 자동 반영하지 않는다.
- 부족이 있으면 자동 후보(감산 수용·대체 원료·긴급 현물·생산일 늦추기)를 만들어 부족·납기 위험·공헌이익 손실·추가 비용을 비교한다. 규칙은 [COMPANY_DATA.md](COMPANY_DATA.md#대응-후보-생산-차질대응안-화면).
- 기존과 대응안을 같은 종료일까지 비교하며 총 계획량 변화도 표시한다. **감산해서 부족이 줄어든 것을 공급 개선으로 취급하지 않는다.**
- 비교 기간은 기준일 이후 최대 366일. 비용과 자동 최적화는 제공하지 않는다.

## 조치 기록과 보호

실제 파일 모드 조치 기록은 `data/company/worklog.sqlite3`에 저장한다. '현장 지시서'의 발주 완료·해동 투입 완료도 상태 '실행 완료'로 같은 곳에 남는다(원본 CSV는 바꾸지 않음). 제목·담당 역할·기한·상태·협의 내용·확인 결과와 연결한 계산 입력·비교 결과를 보존한다. 수정은 기존 기록 삭제가 아니라 새 버전 추가다. 해결 확인에는 결과 근거가 필요하며 수동 기록이지 실제 해결의 자동 인증이 아니다.

샘플 기록은 브라우저 세션 안에만 남고 운영 이력·자동 알림에 섞이지 않는다. 세션이 끝나기 전 JSON으로 내려받을 수 있다. 대응안 JSON과 조치 이력에는 입력 내용이 포함되므로 외부 공유 전에 확인해야 한다.

`.env`의 `COMPANY_PASSWORD`가 설정되면 공장 화면·생산 차질·조치 이력에 같은 잠금을 적용한다. 이는 화면 수준의 단일 비밀번호 보호이며 사용자별 권한·공유 서버 보안이 아니다. 실제 회사 데이터는 공개 서버에 올리지 말고 PC와 파일 접근을 별도로 통제한다. 여러 사용자가 같은 파일을 수정하는 운영 체계는 지원하지 않는다.

원본 CSV 삭제는 화면에서 재확인이 필요하다. 설정·조치 이력은 삭제되지 않는다. 새 CSV 업로드는 해당 원본을 교체하므로 사본을 보관해야 한다.

## 대표 시연

1. **오늘의 생산 위험 → 샘플로 생산 차질 확인**을 누른다. 가짜 데이터임을 확인한다.
2. **생산 차질·대응안**에서 제품별 부족량·부족 원료·납기를 확인한다.
3. 입고 예정의 소 양지 입고일을 앞당긴다. 사용가능일도 변경된 준비 일정에 맞춘다. 이는 공급처가 실제로 동의했다는 뜻이 아니다.
4. 대응안에서 부족량과 납기 위험이 얼마나 바뀌는지 확인한다. 다른 부족 원료가 남았다면 전체 해결로 표현하지 않는다.
5. 생산일을 납기 뒤로 바꿔 원료 부족이 해소되어도 납기 위험이 남는지 확인한다.
6. 대응안을 조치 기록에 연결하고 담당 역할·기한·협의 내용을 남긴다.
7. 같은 사건을 다시 선택해 재계산·해결 확인 기록을 추가한다. 이전 내용과 입력 근거가 남는지 확인한다.

샘플 날짜는 실행일에 따라 달라진다. 개선 수치는 시연 계산 결과일 뿐 실제 회사의 생산 차질 감소율·비용 절감액이 아니다.

## 의도적으로 하지 않은 것

- 생산계획 자동 최적화, 실제 주문·입고·생산실적 자동 반영
- 설비·인력·세척·배치 크기·포장재 제약 및 완제품·운송 계획
- 품질 판정, 해동 안전성 판정, 법적 사용기한 결정
- 비용 최적화(자동 후보는 규칙 기반이며 최소 비용을 찾지 않는다) (원료비 자체는 '원가 영향' 화면에서 계산, 규칙은 [COMPANY_DATA.md](COMPANY_DATA.md#원가-영향-선택-열))
- 여러 사용자 동시 운영·역할별 승인 권한

## 검증 범위

계산 테스트는 공유 원료 중복 배정 방지, 여러 원료의 병목, 냉장·냉동 분리, 검사대기·사용보류 제외, 준비일·기한·기한 우선 사용, 계획 변경·감산·납기 위험, 원본 보존, 설정 저장, 조치 버전 보존을 다룬다.

Streamlit 공식 테스트 실행기로 시장 데이터 없이 오늘 화면 실행, 샘플 대응안 비교·기록 연결, 샘플 이력 저장·수정, 비밀번호 잠금을 검사한다. 실제 브라우저 육안 검증과 모바일 배치 검증을 대체하지는 않는다. 이번 작업에서는 브라우저 도구 접근 제한으로 최신 화면 이미지와 모바일 검증은 수행하지 못했다.

실행: `python -m pytest -q` (저장소 루트). 테스트는 임시 회사 폴더와 가짜 데이터를 사용한다.

2026-10-16 검증 결과: 전체 **83건 통과**. 전체 앱 진입, 저장 설정과 자동 알림 일치, 실제 파일 모드 조치 기록의 새 화면 재열기도 포함한다. 화면 테스트의 임시 파일 생성 권한 문제를 해소한 환경에서 실행했으며 외부 API 수집이나 실제 발주는 실행하지 않았다.
